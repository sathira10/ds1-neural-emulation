\chapter{Training Configuration}
\label{appendix:training-configuration}

This appendix documents the model training configuration used for the Boss DS-1 neural emulation experiment. The setup was implemented in Python on top of the CoreAudioML-style pipeline shipped in the project repository. The aim was to train compact recurrent models that could later be exported from Python and consumed by the JUCE/RTNeural plugin.

\section{Training Environment}

Training ran in a Python workflow built around PyTorch, NumPy, SciPy, Pandas, Matplotlib, TensorBoard-related logging utilities, and the CoreAudioML project modules. The main training notebook imported these internal modules:

\begin{itemize}
  \item \texttt{CoreAudioML.miscfuncs}
  \item \texttt{CoreAudioML.training}
  \item \texttt{CoreAudioML.dataset}
  \item \texttt{CoreAudioML.networks}
\end{itemize}

The notebook was set up to run locally or in Google Colab. In Colab, the repository would be cloned and the working directory changed to the \texttt{model/} folder. Run locally, it used the existing working directory.

The script selected CUDA automatically when a compatible GPU was available, falling back to CPU otherwise. A fixed random seed of 0 was used for both PyTorch and NumPy to keep training behaviour reasonably consistent between runs.

\section{Dataset Loading}

The dataset was loaded from \texttt{model/Data/}. Three subsets were used:

\begin{itemize}
  \item \texttt{Data/train/} for model weight optimisation.
  \item \texttt{Data/val/} for validation during training.
  \item \texttt{Data/test/} for held-out final evaluation.
\end{itemize}

The device name in the training configuration was \texttt{ds1}. The matching files were loaded as input/target audio pairs for each subset, with the dry signal as the model input and the Boss DS-1 processed signal as the target.

Training audio was framed into fixed-length segments of 22,050 samples, which is 0.5 seconds of audio at the project sample rate. The validation and test sets were loaded without that framing step so they could be evaluated over longer continuous chunks.

\section{Model Configurations}

Two recurrent model configurations were trained under matched conditions, one LSTM and one GRU. Both used the same overall SimpleRNN structure, so the recurrent cell type was the main architectural difference between them.

The LSTM model used \texttt{unit\_type = LSTM}; the GRU model used \texttt{unit\_type = GRU}. In both cases the recurrent layer fed a dense output layer that mapped the hidden representation back to a mono audio output. The skip connection let the input signal pass straight through to the output stage while the recurrent model learned the nonlinear transformation needed to approximate the DS-1 response.

The initial recurrent warm-up length lets the hidden state condition itself on the current audio segment before the main loss calculation kicks in. This matters for recurrent audio models because the early output of a segment can otherwise be dominated by an artificially reset hidden state rather than by the learned behaviour of the target device.

\section{Loss Functions}

Training used a weighted loss combining an error-to-signal component and a DC-offset component:

\begin{itemize}
  \item \texttt{ESRPre}: 0.75
  \item \texttt{DC}: 0.25
\end{itemize}

The pre-emphasis filter configuration was:

\begin{verbatim}
[-0.85, 1]
\end{verbatim}

The ESR-based loss compares the energy of the prediction error against the energy of the target signal, which suits audio modelling because the error is then measured relative to how loud the target actually is. The DC component penalises offset differences between the predicted signal and the recorded target. That is useful in distortion modelling, since a learned DC offset can reduce headroom and often points to a bias in the predicted waveform.

The pre-emphasised ESR path puts more weight on frequency-dependent error during training. High-frequency harmonics and transient detail carry a lot of the perceived character of a clipped guitar signal, so emphasising them during training is useful here.

\section{Optimisation and Validation}

Both models were trained with the Adam optimiser. Validation ran every two epochs. A learning-rate scheduler reduced the learning rate when validation improvement slowed, and early stopping was controlled by a validation patience of 25 checks.

During training the notebook stored loss values, validation results, learning-rate history, best-validation information, final test losses, and training time. Each run saved its own statistics into a per-run directory, so the results could be reloaded later without retraining.

The notebook also generated training and validation loss curves, learning-rate plots, per-epoch metric tables, and final comparison tables. These outputs feed into the results chapter and into the LSTM/GRU comparison.

\section{Model Export and Output Files}

Each trained model was saved under the results directory in a folder named after the model type. The LSTM and GRU runs used paths of the form:

\begin{verbatim}
./Results/ds1-LSTM/
./Results/ds1-GRU/
\end{verbatim}

The saved outputs included model JSON files, best-validation model states, generated test audio, and training statistics. The JSON model files contained both architecture metadata and the trained weight values, which is what bridges the Python training stage and the real-time C++ plugin stage.

The notebook also wrote audio examples for comparison: the target test signal, the model output from the final epoch, and the model output from the best-validation checkpoint. These files were used for waveform inspection, spectrogram comparison, and listening checks during development.

\section{Summary}

The configuration is a like-for-like comparison between matched LSTM and GRU SimpleRNN models. Both use mono input and output, one recurrent layer, hidden size 24, and a skip connection. They were trained on matched dry and DS-1 processed audio with a weighted ESR/DC loss, Adam optimisation, validation monitoring, learning-rate scheduling, and early stopping.
