\section{Methodological Overview}
\label{sec:methodological-overview}

This project uses a practice-based research methodology in which the production of technical artefacts is treated as part of the research process. The study does not only evaluate an existing software tool; it designs and documents an end-to-end neural emulation workflow for a physical Boss DS-1 distortion pedal. The principal artefacts of the methodology are the matched dry and processed recordings, the trained recurrent neural network models, the exported model weight files, and the JUCE/RTNeural plugin implementation. These artefacts are used both to investigate the research question and to demonstrate the practical feasibility of deploying compact neural audio models in a real-time digital audio workstation environment.

The methodology follows the full path from hardware capture to real-time software deployment. First, audio material is recorded as paired examples of dry guitar input and Boss DS-1 processed output. These recordings are then organised into training, validation, and test datasets. Compact recurrent neural networks are trained in Python to predict the processed DS-1 signal from the corresponding dry input signal. The trained weights are exported to a JSON format and loaded into a C++ audio plugin, where inference is performed using RTNeural inside a JUCE-based real-time audio processor.

The study is comparative because two recurrent architectures, the long short-term memory network (LSTM) and the gated recurrent unit (GRU), are trained and deployed under matched conditions. The purpose of this comparison is not to claim that either architecture is generally superior, but to examine their relative suitability for this specific DS-1 emulation task. Accuracy, parameter count, export compatibility, and real-time deployment behaviour are therefore considered together. This allows the research question to be addressed as both a modelling problem and a practical audio engineering problem.

\section{Research Artefacts and Repository}
\label{sec:research-artefacts-repository}

The implementation artefacts for this project are organised in an accompanying software repository. The repository contains the Python training pipeline, dataset directory structure, exported model files, JUCE/RTNeural plugin source code, and LaTeX thesis material. The repository is treated as part of the practice-based research output because it documents the complete path from DS-1 recording and model training to real-time plugin deployment.

The repository is available at:

The repository version used for the final dissertation submission is identified by the Git tag \texttt{thesis-submitted}. This tag marks the repository state corresponding to the version submitted for examination. Using a fixed repository tag is important because it ties the written thesis to a stable state of the implementation. If the repository continues to change after submission, the tag allows the submitted artefact to be distinguished clearly from later development work.

The first research artefact is the matched recording dataset. This dataset consists of original dry guitar recordings and corresponding wet recordings captured through the physical Boss DS-1 pedal. The dry recording acts as the model input and the processed DS-1 recording acts as the target output. Because the recordings are paired, the modelling task can be treated as supervised learning: the network is trained to reproduce the pedal output for a known input signal.

The second artefact is the Python training pipeline located under the \texttt{model/} directory. This pipeline follows a CoreAudioML-style PyTorch workflow and provides the dataset loading, recurrent model definition, loss computation, training loop, validation process, logging, and model export functionality used in the experiment. It is the offline research environment in which the LSTM and GRU models are trained and evaluated before deployment.

The third artefact is the exported model representation. Trained models are written as JSON files that contain both architecture metadata and trained weight values. This export step is methodologically important because it forms the bridge between the Python training environment and the real-time C++ plugin environment. The plugin does not depend on Python or PyTorch at runtime; instead, it loads the exported model description and weights into RTNeural-compatible structures.

The fourth artefact is the JUCE/RTNeural plugin. This plugin provides the deployment context for the trained recurrent models and allows the models to be tested as real-time audio processors. It exposes user-facing parameters for Drive, Level, Model selection, and Bypass, and it embeds the exported LSTM and GRU models as plugin resources. The plugin therefore demonstrates whether the trained models can move beyond offline analysis and operate in a real-time audio callback.

The final artefact is the written thesis documentation. The dissertation explains the technical decisions, methodological boundaries, implementation state, and limitations of the project. This is necessary because the artefact alone does not fully communicate the research design. The written component clarifies what was controlled, what was measured, what remains outside the scope, and how the implementation should be interpreted.

\section{Dataset Design and Recording Scope}
\label{sec:dataset-design-recording-scope}

The dataset was designed to support a controlled comparison between recurrent model architectures. All captures were made using a single physical Boss DS-1 distortion pedal. The pedal controls were held at a fixed setting, with Tone, Distortion, and Level all positioned at 12 o'clock. This fixed configuration reduces variation in the target system so that the trained models are compared against the same captured pedal response.

The paired dataset contains dry input audio and corresponding target audio processed through the DS-1. The dry audio provides the input sequence for the neural network. The wet DS-1 recording provides the target sequence that the network attempts to predict. The source material included both electric guitar and bass guitar performances, covering practical variations such as single notes, chordal playing, palm-muted attacks, sustained notes, and changes in picking dynamics. This input-output structure is appropriate for black-box modelling because the model is not given an explicit circuit description. Instead, it learns the relationship between the dry signal and the processed signal from recorded examples.

The dataset is organised into three splits under the training pipeline: \texttt{model/Data/train}, \texttt{model/Data/val}, and \texttt{model/Data/test}. The training set is used for weight updates during model optimisation. The validation set is used to monitor generalisation during training, control learning-rate scheduling, and support early stopping. The test set is held back for final objective evaluation and should not be used to tune model parameters or choose training settings.

This dataset design supports a focused and controlled experiment, but it also defines the limits of the model. Because only one DS-1 pedal and one knob setting are captured, the trained models should be understood as emulations of that specific recorded condition. They do not model the full range of the DS-1 controls, do not account for unit-to-unit hardware variation, and do not guarantee equivalent performance on playing styles or signal conditions that are absent from the dataset. These limits are intentional: they narrow the research scope so that the GRU and LSTM comparison can be made under matched conditions.

\section{Training Pipeline}
\label{sec:training-pipeline}

The main training entry point is \texttt{model/script.py}. This script loads configuration values from JSON files in \texttt{model/Configs/}, reads matched audio pairs from the dataset directories, constructs the selected recurrent model, trains the model, evaluates validation performance, and writes output artefacts to the results directory. The training workflow is therefore reproducible from repository configuration rather than being defined only by manual notebook experimentation.

Audio is framed into fixed-length segments for training. The current segment length is 22,050 samples, which corresponds to 0.5 seconds at a 44.1 kHz sample rate. Segmenting the audio in this way makes mini-batch training practical while still giving the recurrent model enough temporal context to learn short-term nonlinear and memory-dependent behaviour. Each segment contains aligned input and target audio so that sample-wise prediction error can be computed.

A recurrent warm-up strategy is used during training. At the beginning of a segment, an initial sequence length is processed to establish the model's hidden state before the main loss calculation is applied. This is important because recurrent models depend on hidden state. If loss were applied immediately from an unconditioned state, the early part of each segment could include error caused by artificial state initialisation rather than by the model's ability to emulate the pedal. The warm-up section helps the recurrent state become informed by the current audio context before optimisation focuses on prediction accuracy.

The optimisation setup uses the Adam optimiser with validation monitoring, learning-rate scheduling, early stopping patience, and TensorBoard logging. Adam is used because it provides adaptive gradient-based optimisation suitable for neural network training. Validation checks are performed during training to monitor whether the model is improving on unseen data. A learning-rate scheduler reduces the learning rate when validation improvement stagnates, allowing training to continue with smaller updates. Early stopping prevents unnecessary training once validation performance stops improving for a defined patience period.

Training writes several forms of output under \texttt{model/Results/}. These include exported model JSON files, best-validation checkpoints, generated test audio, and training statistics. These outputs support both Chapter 4 results reporting and the plugin deployment stage. The exported JSON models are especially important because they are the files transferred into the plugin resource path for C++ inference.

\section{Model Architecture}
\label{sec:model-architecture}

The active architecture is a compact \texttt{SimpleRNN} sequence model. The model receives a mono input sequence, processes it through one recurrent layer, maps the recurrent output through a dense linear output layer, and produces a mono predicted target sequence. An optional skip connection can pass the input directly to the output stage, allowing the model to learn the nonlinear difference between dry and processed signals while retaining a direct signal path.

The recurrent layer is either an LSTM or a GRU. This is the main experimental variable in the architecture comparison. The rest of the model structure is kept constant so that differences in training behaviour, parameter count, and deployment suitability can be meaningfully attributed to the recurrent cell type. In both cases, the model operates as a black-box emulator of the DS-1 rather than a physically interpretable circuit simulation.

The current plugin-compatible configuration uses an input size of 1, output size of 1, one recurrent layer, hidden size 24, and skip connection enabled. This configuration is deliberately compact. A smaller model reduces parameter count and supports real-time deployment, while still providing recurrent state for modelling temporal behaviour. The matched LSTM and GRU configurations therefore allow a practical comparison between a higher-parameter gated recurrent cell and a lower-parameter gated recurrent cell.

The architecture is causal because the output at each time step depends only on the current input sample and the model's previous hidden state. It does not require future samples. This is a necessary property for low-latency audio plugin use because a real-time processor cannot depend on audio that has not yet arrived from the host. The recurrent state is carried across samples, allowing the model to represent short-term memory effects while remaining suitable for sample-by-sample inference.

\section{Losses and Evaluation Metrics}
\label{sec:losses-evaluation-metrics}

The main objective loss used in the project is Error-to-Signal Ratio (ESR). ESR measures the energy of the prediction error relative to the energy of the target signal. In this context, the prediction error is the difference between the neural model output and the recorded DS-1 target output. Lower ESR values indicate that the predicted waveform is closer to the recorded target waveform in an energy-normalised sense.

DC loss is used as a supplementary term. This loss penalises mismatch in the average or low-frequency offset between the model output and the target signal. DC offset is important in audio modelling because a model could produce a waveform that has a similar general shape but includes an unwanted bias. Such a bias may reduce technical audio quality and may cause problems when the model output is used in a plugin signal chain.

The final objective evaluation is carried out on the held-out test set. The training set is used for optimisation and the validation set is used for monitoring and model selection, so neither is treated as the final measure of generalisation. The test set provides a more appropriate estimate of how well the trained model reproduces target material that was not used for weight updates or validation-driven decisions.

Parameter count is included as an efficiency metric because real-time deployment is part of the research question. The implemented LSTM model contains 2,617 parameters, while the corresponding GRU model contains 1,969 parameters. This difference reflects the recurrent cell structures: an LSTM uses more gate groups than a GRU and therefore requires more weights for the same hidden size. Parameter count does not fully determine CPU cost, but it is a useful indicator of model compactness and deployment efficiency.

ESR and DC loss are objective metrics. They are useful for comparing model outputs against recorded target waveforms, but they do not replace formal perceptual evaluation. A lower objective error does not automatically prove that a model is perceptually indistinguishable from the hardware pedal. Conversely, some waveform differences may be audible only weakly or may be musically acceptable. For this reason, the evaluation in this project is objective and technical rather than a formal listening study.

\section{Model Export and Validation}
\label{sec:model-export-validation}

The trained models are exported in a CoreAudioML-style JSON format. Each JSON file contains architecture metadata and a \texttt{state\_dict} containing the trained weights. The metadata describes how the model should be reconstructed, while the weight arrays provide the learned values for the recurrent and dense layers. This separation allows the plugin loader to verify that the file describes a supported architecture before attempting to use the weights in real-time inference.

The key metadata that must remain explicit includes the model class, recurrent unit type, hidden size, input size, output size, number of recurrent layers, skip connection state, and sample rate. These values are not incidental. They define whether the exported model is compatible with the plugin's statically typed inference path. A mismatch between the exported architecture and the plugin implementation could lead to incorrect inference, failed loading, or unstable runtime behaviour.

After training, selected exported models are copied or embedded into the plugin resource directory, \texttt{plugin/Resources/Models/}. This directory contains the JSON files used by the plugin build. During plugin compilation, the model files can be embedded as binary resources so that the deployed plugin contains the trained LSTM and GRU weights without needing to locate external files at runtime.

The plugin loader validates the JSON before use and rejects unsupported architectures. In the current implementation, the plugin-compatible model is restricted to a mono \texttt{SimpleRNN} with one recurrent layer, hidden size 24, supported unit type, and valid skip connection setting. This validation step is methodologically important because it prevents the deployment result from depending on unverified assumptions about the model file. It also makes the boundary between the training artefact and deployment artefact explicit.

\section{Plugin Deployment Method}
\label{sec:plugin-deployment-method}

The deployment stage uses a plugin stack consisting of C++23, JUCE, RTNeural, CMake, and a React/Vite WebUI. JUCE provides the audio plugin framework and host integration. RTNeural provides a C++ inference path for running the exported recurrent models in real time. CMake manages the plugin build and resource embedding process. The React/Vite WebUI provides the graphical control surface used by the plugin.

The plugin exposes four main audio parameters: Drive, Level, Model, and Bypass. Drive controls the gain applied before neural processing. Level controls the output gain after processing. Model selects between the embedded LSTM and GRU models. Bypass allows the processed output to be crossfaded with the unprocessed signal rather than abruptly switched. Together, these controls provide a practical interface for testing the trained neural emulations in a DAW.

The audio callback follows a real-time signal path. The incoming audio is gain-adjusted by the Drive control, the active model is selected, stereo input is summed to mono for neural inference, the recurrent model processes the mono signal sample by sample, bypass crossfading is applied, and the final output is scaled by the Level control. The processed mono output is then returned to the plugin output channels. This design reflects the mono nature of the trained model while allowing the plugin to function in a stereo host context.

Drive, Level, and Bypass are smoothed to reduce clicks and discontinuities during parameter changes. This is important because abrupt gain or bypass changes can introduce unwanted transient artefacts. Model switching also resets the incoming model's hidden state to reduce switching artefacts caused by stale recurrent state. These details are part of the deployment method because they affect whether the neural model can be used as a practical real-time audio processor rather than only as an offline prediction model.

\section{Sample-Rate Handling Requirement}
\label{sec:sample-rate-handling-requirement}

The neural models are trained at 44.1 kHz, so model inference should occur at 44.1 kHz. This requirement follows from the temporal nature of recurrent audio models. The model learns relationships between samples at the training sample rate, and its hidden state evolves according to that sample-by-sample timing. If the same model is run directly at a different host sample rate, the time scale of the learned response changes.

The required real-time signal path is therefore: host sample rate to 44.1 kHz, neural model inference at 44.1 kHz, and 44.1 kHz back to the host sample rate. For a DAW session running at 48 kHz, 96 kHz, or another rate, the wet-path signal should be converted before it reaches the recurrent model and converted back before it is mixed into the plugin output. Without this conversion, the model may be driven at the wrong temporal rate, which could alter the effective response of the emulation.

Within this project, this sample-rate conversion path is identified as a required engineering step rather than a completed part of the deployed artefact. The reported runtime validation is therefore limited to 44.1~kHz host sessions, where the host rate matches the model training rate.

The implementation constraints are significant because the process occurs in a real-time audio callback. The resampler must avoid audio-thread allocation, maintain persistent state across processing blocks, reset cleanly during \texttt{prepareToPlay()} and model or transport resets, and report any additional latency to the host if latency is introduced. These constraints make sample-rate handling a plugin engineering issue as well as a modelling issue.

\section{Methodological Limitations}
\label{sec:methodological-limitations}

The first limitation is that only one physical DS-1 unit is modelled. Analog pedals can vary due to component tolerances, manufacturing differences, age, and condition. The trained models therefore represent the captured behaviour of the specific pedal used in this project rather than all DS-1 pedals.

The second limitation is that only one knob setting is captured. Tone, Distortion, and Level are fixed at 12 o'clock, so the resulting models are not parameter-conditioned across the DS-1 control range. The Drive and Level parameters in the plugin provide practical gain control around the model, but they do not make the neural network a full model of the pedal's physical knobs.

The third limitation is that objective waveform metrics do not establish perceptual indistinguishability. ESR and DC loss provide useful technical evidence, but a formal listening study would be required to make stronger perceptual claims. Future work could extend the evaluation using ABX or MUSHRA-style tests with guitarists, engineers, or trained listeners.

The fourth limitation is that plugin testing is artefact validation rather than full commercial quality assurance. The plugin demonstrates the deployment path from trained model to real-time processor, but this does not imply exhaustive testing across all DAWs, operating systems, sample rates, buffer sizes, and session conditions. It is therefore presented as a research artefact that validates the workflow rather than as a finished commercial product.
